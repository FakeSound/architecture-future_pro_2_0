# Обоснование событийного подхода — Будущее 2.0

## Текущее состояние: Apache Camel ESB + SQL Server DWH

Текущая интеграция строится на двух механизмах:

- **Apache Camel ESB** — синхронная шина, через которую системы обмениваются данными в режиме запрос/ответ. Изменение одного маршрута требует знания всех его участников.
- **SQL Server 2008 DWH** — централизованное хранилище, в которое данные поступают пакетными ETL-загрузками. Данные для аналитики доступны с задержкой от нескольких часов до суток.

### Проблемы текущего подхода

| Проблема                     | Следствие                                                      |
|------------------------------|----------------------------------------------------------------|
| Синхронная связность (Camel) | Падение одной системы блокирует весь маршрут                   |
| Централизованная оркестрация | Добавление нового участника — изменение существующего маршрута |
| Пакетные ETL (DWH)           | Аналитика работает на вчерашних данных                         |
| Монолитная схема DWH         | Все домены зависят от единой модели данных                     |
| SQL Server 2008              | End-of-life, нет поддержки, угроза безопасности                |

## Целевой подход: событийная архитектура на Apache Kafka

Домены публикуют события о произошедших фактах. Подписчики реагируют самостоятельно, без центральной оркестрации.

### Преимущества для Будущего 2.0

#### 1. Независимость доменов
Медицинский домен публикует `appointment.completed` и не знает, кто на него подписан. Финтех-домен получает событие и инициирует оплату самостоятельно. Добавление нового подписчика (например, аналитика выручки) не требует изменения Clinical Services API.

По сравнению с Camel: добавление нового маршрута в ESB затрагивало существующую конфигурацию. Теперь это изолированное изменение.

#### 2. Масштабируемость под рост

Kafka позволяет горизонтально масштабировать как продюсеров, так и консьюмеров независимо. При росте нагрузки (новые клиники, новые регионы) добавляются партиции и консьюмер-группы — без остановки системы.

Camel ESB масштабируется как монолит: вертикально и с ограниченной изоляцией нагрузки между маршрутами.

#### 3. Аналитика в реальном времени

Apache Flink потребляет события напрямую из Kafka и формирует витрины с задержкой в секунды. Руководство клиник видит текущую загрузку, финансовые показатели обновляются по факту платежа.

По сравнению с DWH: ETL-загрузка раз в ночь давала данные с задержкой 12–24 часа. Это неприемлемо для оперативных управленческих решений.

#### 4. Устойчивость к сбоям

Если AI Services временно недоступны, события `diagnosis.added` накапливаются в Kafka и обрабатываются после восстановления. DLQ изолирует проблемные сообщения без остановки остального потока.

В Camel: синхронный вызов недоступного сервиса возвращал ошибку вызывающей стороне. Требовалась ручная логика повторов.

#### 5. Онбординг новых доменов

Новый домен (например, лабораторные услуги) подключается как подписчик уже существующих событий Clinical и публикует собственные события. Это не затрагивает другие домены.

В ESB: подключение нового участника требовало проектирования и развёртывания нового маршрута с тестированием всей цепочки.

#### 6. Разделение операционного и аналитического слоёв

Домены работают со своими операционными БД (PostgreSQL). Data Platform независимо потребляет события и строит аналитику. Нагрузка аналитических запросов не влияет на производительность операционных систем.

В DWH-подходе: аналитические запросы и ETL конкурировали за ресурсы того же SQL Server, что вызывало деградацию операционных систем в часы пиковой нагрузки.

## Компромиссы и меры управления

Событийная архитектура вводит **eventual consistency**: состояние подписчиков обновляется с небольшой задержкой. Это осознанный выбор, но требует проектирования:

- Для критичных cross-domain процессов (например, оплата + разблокировка услуги) обязательно проектировать **saga pattern** с компенсирующими транзакциями
- Schema Registry обеспечивает контрактную совместимость событий при эволюции схем
- Операционная сложность Kafka выше, чем у простого ESB — требует выделенной экспертизы и observability с первого дня
